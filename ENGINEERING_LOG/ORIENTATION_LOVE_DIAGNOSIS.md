## 〇、结论（更正后）

```
① ✅ **模型是对的**："双性恋"这一类**本来就有**（`ORI_NAME[2]` · `ORI_BI = 1.0%`），
   `canLove` 的规则是"任一方双性恋 ⇒ 允许；任一方同性恋 ⇒ 须同性；双方异性恋 ⇒ 须异性"，
   且**建立关系的三条入口全部过它**（恋爱 :4295 · 婚外情 :4339 · 恋爱转婚姻 :4460 更严）。
   ⇒ ⭐ **不需要"再定义一个双性恋"**；一个人恋人男女都有 ⇒ 在模型里他就该是 `ori=2`。

② ⚠⚠ **真正的缺陷是【前端可读性】**（这才是用户看到怪现象的原因）：
   · ⭐ `/api/citizen` 的 **lover 对象不带 `ori`** ⇒ 页面上**无法看出"对方是同性恋/双性恋"**
     ⇒ 于是"看到同性恋人"时，用户**没有任何办法当场判断它是否合理** ⇒ 只能怀疑模型坏了。
   · 🔴 **`/api/citizen` 对【无效 ID】返回 200 + 随机一个人**（本地源码 `city_server.js:931-933`：
     `if (idx < 0) { 随机挑一个 alive }`）⇒ ⭐ **"你要看的不是你看的那个人"这件事是静默的**：
     点恋人、点配偶、点子女、手输 ID —— **任何一次 ID 不匹配，页面都会换一个人**，
     而页面标题仍是你点的名字 ⇒ **两条互不相干的记录被当成一个人的证据**。
   · ⭐ **"性取向：异性恋"这三个字是硬兜底**：线上 `client.min.js` 里是
     `${d.oriName||"异性恋"}` ⇒ `oriName` 一旦缺失就显示"异性恋"。
```

## 三、⚠ 一条"没查实"的可能性（如实 · 未证实）

```
⚠ **"按 id 补齐取向"这条路径会换人**（机制成立、但【未必是本次现象的原因】）：
   city_server.js:414-416  若 city.ori 缺失 ⇒ `city.ori[i] = CIV.cityDrawOri(CIV.makeRng(city.id[i] + 991), gen[i])`
   ⭐ 实测（`_ori_reload_check.cjs` · 对线上快照那 99.7 万人）：
      "快照里存的 ori" 与 "该补齐公式算出的 ori" **不同 = 121,062 人（12.14%）**
   ⇒ ⭐ **该公式与原仿真抽取向【不是同一股随机流】** ⇒ **若某次快照真的丢了 `ori`，
     全城取向会被重抽一遍（其中 12% 会换），而【恋爱配对是按 id 保存的、不会跟着变】**
     ⇒ 那就会出现"取向与配对矛盾"。
   ⚠ **但本次未观测到该状态**：三方实测都合规 ⇒ **只能列为"潜在隐患"**，不能当成已发生的 bug。
   ✅ **加固建议（便宜且彻底）**：把取向也**按 ID 落进快照**（与 `lifeLog` / `love` 同一做法）
      —— 一旦如此，"重抽公式与原公式不一致"就再也无法造成损害。
```

## 四、建议的修法（按性价比）

```
① ⭐⭐ **`/api/citizen` 对无效 ID 返回 404 / 明确错误**（现在是静默返回随机人）
   ⇒ 这条是**一切"看错人"现象的根**，且本地早已列为待办（HANDOFF §五·8）
② ⭐⭐ **lover / spouse / children 对象补上 `ori` + `oriName`**
   ⇒ 用户一眼能看出"对方是双性恋"，不必手点；也顺便消灭"看起来自相矛盾"的观感
③ ⭐ **前端兜底 `|| "异性恋"` 改成 `|| "未标注"`**
   ⇒ 不要用一个**断言**去填一个**未知**
④ ✅ 模型侧：**不需要改 `canLove`、不需要新增性别类别**（双性恋已存在）
⑤ ⚠ 加固（可选）：取向按 ID 持久化（见 §三）
```
